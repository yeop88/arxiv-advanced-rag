# 발표 자료 — arXiv Advanced RAG

PPT를 만들 때 쓰는 슬라이드별 구성안입니다. 각 슬라이드에 **화면에 넣을 내용**, **그림**, **발표 대본**을 적었습니다.
그림은 `charts/` 폴더에 있고 `python docs/presentation/make_charts.py`로 다시 만들 수 있습니다.
수치 출처는 [ACHIEVEMENT.md](../ACHIEVEMENT.md)와 [PROGRESS_REPORT.md](../PROGRESS_REPORT.md)입니다.

- 분량: 14장, 발표 약 12~15분
- 흐름: 문제 → 해결 구조 → 측정으로 내린 결정 → 자동 수집 → 달성률 → 다음 방향

---

## 1. 표지

**화면**
- arXiv Advanced RAG
- 근거로 답하고, 근거가 없으면 스스로 찾아오는 논문 어시스턴트
- 이름 · 날짜

**대본**: 영어 논문을 근거로 한국어 질문에 답하는 RAG 시스템을 만들었습니다. 오늘은 무엇을 만들었는지보다 어떻게 측정하며 결정했는지를 중심으로 말씀드리겠습니다.

## 2. 왜 필요한가

**화면** (문제 5개, 한 줄씩)
1. 논문이 너무 빨리 쌓인다
2. 일반 챗봇의 답은 확인하기 어렵다 — 없는 인용을 만든다
3. 논문은 대부분 영어다
4. 모델은 학습 이후의 논문을 모른다
5. 자료를 외부로 보내기 어려운 환경이 있다

**대본**: 연구에서는 그럴듯한 오답의 비용이 큽니다. 그래서 답의 출처를 원문까지 되짚을 수 있어야 하고, 모르면 모른다고 해야 합니다.

## 3. 해결 구조 — 0~4단계 파이프라인

**화면** (가로 흐름도로 그리기)
`0 문맥화 → 1 질의 변환 → 2 검색·리랭크 → 3 생성 → 4 검증` (+ 근거 부족 시 자동 수집 → 다시 2단계)

| 단계 | 하는 일 | 모델 |
|---|---|---|
| 0 문맥화 | 멀티턴 대화의 후속 질문을 독립 질문으로 | LLM(경량) |
| 1 질의 변환 | 한국어 질문 → 영어 검색어 3개 | LLM(경량) |
| 2 검색·리랭크 | 의미 검색 + 키워드 검색(BM25) 결합 → 리랭커 → 다양성 선택 | bge-m3, bge-reranker-v2-m3 (로컬) |
| 3 생성 | 근거만 사용, 문장마다 [n] 인용 | LLM |
| 4 검증 | 근거와 대조해 채점, 실패하면 재작성 | LLM |

**대본**: 검색은 로컬 모델이라 비용이 들지 않고, 판단만 LLM이 합니다. LLM은 Claude, OpenAI, 로컬 모델을 설정 한 줄로 바꿀 수 있습니다.

## 4. 데모 화면

**화면**: 챗봇 스크린샷 2장
- 인용이 달린 답변과 근거 패널
- 진행 로그(만든 검색어, 고른 논문, 검증 결과)

**준비**: `streamlit run app.py` 실행 후 "KAN과 MLP 구조 차이"처럼 자동 수집이 일어나는 질문으로 캡처.

**대본**: 질문하면 각 단계에서 무엇을 했는지가 실시간으로 보입니다. 답의 [1], [2]를 누르면 원문 청크를 확인할 수 있습니다.

## 5. 평가 체계 — 감이 아니라 수치로

**화면**
- 평가셋 294문항(어려운 다중 홉 질문 포함)
- 검색 지표: recall@5, MRR — LLM 없이 무료로 반복 측정
- 답변 지표: faithfulness, answer relevance, context relevance — LLM 채점
- 2단 평가: 값싼 검색 지표로 걸러 내고, 대표 표본만 LLM으로 확인

**대본**: 모든 변경은 같은 평가셋으로 전후를 비교했습니다. 다음 장이 그 덕분에 잘못된 결정을 되돌린 사례입니다.

## 6. 측정이 결정을 뒤집은 사례 (ADR-001)

**그림**: `charts/02_query_transform.png`

**화면 요점**
- 10문항으로는 HyDE가 가장 좋아 보여 기본값으로 채택
- 111문항으로 늘리자 HyDE가 가장 낮음(어려운 문항 0.839 vs 0.935)
- multi_query + 하이브리드로 되돌리고, 답변 지표로도 다시 확인

**대본**: 작은 표본의 차이는 대부분 잡음이었습니다. 평가셋을 키우는 것 자체가 가장 큰 개선이었습니다.

## 7. 검색 품질 개선 요약

**화면** (표)

| 개선 | 효과 |
|---|---|
| 하이브리드 검색(BM25 + 벡터) | 모델명·약어 질문에 강해짐 |
| 다양성 리랭킹(MMR, 논문당 2청크) | 다중 홉 recall@5 0.794 → 0.850 |
| 저장 벡터 재사용 + GPU fp16 | 리랭크 구간 4.74초 → 0.06초 |
| 현재 검색 수준(294문항) | recall@5 0.9694, MRR 0.9521 |

**대본**: 다양성 리랭킹은 공짜가 아니었습니다. recall은 올랐지만 근거의 평균 관련도는 0.08 내려갔고, 다중 홉 질문을 위해 이 손해를 감수했습니다.

## 8. 로컬 모델로 전체 실행

**그림**: `charts/05_latency.png`

**화면 요점**
- 로컬 Qwen3.6-35B로 전 단계 실행, 외부 LLM API 없이 동작
- 질문당 평균 62초, 대부분 생성·검증
- 어려운 69문항: faithfulness 0.994, 답변률 97%
- 주의: 로컬 모델이 자기 답을 채점한 값

**대본**: 자료를 외부로 보낼 수 없는 환경에서도 쓸 수 있다는 걸 확인했습니다. 다만 채점도 같은 모델이 해서, Claude와 같은 조건으로 비교한 것은 아닙니다.

## 9. 자기 확장 RAG — 근거가 없으면 찾아온다

**화면** (흐름도)
1. 근거 부족 감지: 리랭크 최고 점수 < 0.2, 또는 답변이 "찾을 수 없다"
2. 영어 검색어로 arXiv·OpenAlex 검색(인용 수 순 포함)
3. 초록 관련도 0.3 이상, 최대 3편, 가장 많이 인용된 논문 우선
4. PDF 전문을 DB에 추가(참고문헌·부록 제외) → 다시 검색·답변

**예시**: KAN 질문 — 최고 점수 0.006 → 수집 후 0.990, 원 논문으로 정확히 답함

**대본**: "찾을 수 없습니다"로 끝나지 않고 직접 논문을 찾아 DB를 키웁니다. 무관한 질문에는 논문을 넣지 않았고, 같은 질문을 다시 해도 중복 수집하지 않았습니다.

## 10. 자동 수집의 부작용과 관리

**그림**: `charts/03_corpus_growth.png`

**화면 요점**
- 수집 논문이 다른 질문의 근거에 끼어듦 → 원인의 68%가 참고문헌·부록 → 제외
- 수집 논문 점수에 0.7 가중치 → 기존 논문 우선
- 코퍼스가 커질수록 조금씩 하락 → 예산 2,000청크, 오래 안 쓴 논문부터 자동 정리
- 상태 점검 스크립트로 정상/주의/초과 판정

**대본**: 스스로 커지는 시스템은 스스로 나빠질 수도 있습니다. 크기별로 측정해 허용 한도의 절반 수준에서 멈추도록 예산을 정했습니다.

## 11. 자동 수집 성적표

**그림**: `charts/06_kpi_table.png`, `charts/04_auto_fetch_progress.png`

**화면 요점**
- 8개 기준 중 6개 통과(기존 품질 유지, 무관한 수집 0, 재수집 0)
- 미달 2개: 원 논문 수집 45%(목표 60%), 불필요한 수집 신호 23%(목표 5%)
- 시나리오 시험: 다른 분야 10개·영어·멀티턴·이상한 입력·장애·동시 질문 — 오류 없음

**대본**: 미달 항목을 숨기지 않았습니다. 유명한 오래된 논문일수록 검색 결과에서 파생 논문에 밀리는 게 주된 원인입니다.

## 12. 달성률

**그림**: `charts/01_achievement.png`

**화면 요점**
- 현재 목표 20개: **95%** (달성 18, 부분 2)
- 로드맵 15개: **17%** (부분 5, 미착수 10)
- 부분 달성 2개는 모두 자동 수집의 정확도

**대본**: 지금 해야 할 일은 거의 이뤘고, 로드맵은 단기 과제 일부만 손댔습니다. 기능을 늘리기보다 측정과 품질 관리에 시간을 썼기 때문입니다.

## 13. 한계와 배운 점

**화면**
- 한계: 평가셋이 실제 질문보다 쉬울 수 있음 / 로컬 모델 자기 채점 / 한국어 키워드 검색 약함 / PDF 표·수식 미지원

  3. 무료 서비스에도 숨은 한도가 있다 — 벡터 DB 전송량 한도로 로컬 전환

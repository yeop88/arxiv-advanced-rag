수치 출처는 [ACHIEVEMENT.md](../ACHIEVEMENT.md)와 [PROGRESS_REPORT.md](../PROGRESS_REPORT.md)(§ 번호)입니다.

- 기준일: 2026-11-15 (2026-11-09 시작)
- 분량: 19장, 발표 약 17분
- 흐름: 문제 → 해결 구조 → 측정으로 내린 결정 → **업데이트 6번으로 본 개선 과정** → 시험 질문 사례 → 달성률 → 다음 방향
- 작성 원칙: 개선은 하나씩 나열하지 않고 주제별 **업데이트 묶음**으로 보여 준다. 묶음마다 대표 코드 변화 1개 + 측정 결과 표.

## 1. 표지

**화면**
- arXiv Advanced RAG
- 근거로 답하고, 근거가 없으면 스스로 찾아오고, 답의 문장마다 근거를 확인하는 논문 어시스턴트
- 이름 · 날짜

**대본**: 영어 논문을 근거로 한국어 질문에 답하는 RAG 시스템입니다. 무엇을 만들었는지보다, 측정하면서 코드를 어떻게 바꿔 왔는지를 중심으로 말씀드리겠습니다.

## 2. 왜 필요한가

**화면** (문제 5개, 한 줄씩)
1. 논문이 너무 빨리 쌓인다
2. 일반 챗봇의 답은 확인하기 어렵다 — 없는 인용을 만든다
3. 논문은 대부분 영어다
4. 모델은 학습 이후의 논문을 모른다
5. 자료를 외부로 보내기 어려운 환경이 있다

**대본**: 연구에서는 그럴듯한 오답의 비용이 큽니다. 답의 출처를 원문까지 되짚을 수 있어야 하고, 모르면 모른다고 해야 합니다.

## 3. 해결 구조 — 0~4단계 파이프라인

**화면** (가로 흐름도로 그리기)
`0 문맥화 → 1 질의 변환 → 2 검색·리랭크 → 3 생성 → 4 검증 → 4b 문장 단위 인용 확인` (+ 근거 부족 시 자동 수집 → 다시 2단계)

| 단계 | 하는 일 | 모델 |
|---|---|---|
| 0 문맥화 | 멀티턴 대화의 후속 질문을 독립 질문으로 | LLM(경량) |
| 1 질의 변환 | 한국어 질문 → 영어 검색어 3개 | LLM(경량) |
| 2 검색·리랭크 | 의미 검색 + 키워드 검색(BM25) 결합 → 리랭커 → 다양성 선택 | bge-m3, bge-reranker-v2-m3 (로컬) |
| 3 생성 | 근거만 사용, 문장마다 [n] 인용 | LLM |
| 4 검증 | 근거와 대조해 채점, 실패하면 재작성 | LLM |
| 4b 인용 확인 | 문장마다 인용한 근거와 대조, 숫자는 원문과 규칙 대조 | 리랭커 (LLM 없음) |

**대본**: 검색과 인용 확인은 로컬 모델이라 비용이 들지 않고, 판단만 LLM이 합니다. LLM은 설정 한 줄로 바꿀 수 있고, 지금은 로컬 Qwen3.6만 씁니다.

## 8. 업데이트 ① 검색 품질

**그림**: `charts/08_reranker_title.png`

**대표 코드 변화** (`rag/stages/stage2_rerank.py`) — 리랭커가 본문 문단이 어느 논문인지 알게
```python
# 전
pairs = [(question, c.content) for c in candidates]
# 후: 저장 글·LLM 근거는 그대로, 리랭커만 "논문 제목\n본문"을 본다
pairs = [(question, rerank_input(c)) for c in candidates]
```

**이 업데이트에 묶인 개선과 결과**

| 개선 | 결과 |
|---|---|
| 하이브리드 검색(BM25 + 벡터, RRF) | 모든 설정에서 벡터만보다 우위 |
| 다양성 리랭킹(MMR, 논문당 2청크) | 다중 홉 recall@5 0.733 → 0.800 |
| 한국어 키워드 검색("HyDE의" → "hyde") | MRR 0.9485 → 0.9543 |
| 리랭커에 논문 제목 | MRR 0.9545 → 0.9700, 다중 홉 recall +0.01 |

**대본**: 논문 제목을 임베딩까지 넣으면 MRR은 더 오르지만 다중 홉 recall이 떨어져 보류했고, 리랭커에만 넣는 방식을 골랐습니다(그래프 왼쪽 vs 오른쪽). 좋아 보여도 다른 지표를 깎으면 넣지 않았습니다.

## 9. 업데이트 ② 자기 확장 — 근거가 없으면 찾아온다

**그림**: `charts/03_corpus_growth.png`

**화면** (흐름)
근거 부족 감지(리랭크 최고 점수 < 0.2 또는 "찾을 수 없다") → 원 논문 제목 추정 + arXiv 검색 → 관련도 0.3 이상 → PDF 전문 추가 → 다시 답변

**대표 코드 변화** — 수집한 논문이 무관한 질문의 근거를 흐리던 문제
```python
# 전
c.rerank_score = float(s)
# 후: 자동 수집 논문은 0.7배 → 기존 논문 우선 (+ 참고문헌·부록은 아예 넣지 않음)
c.rerank_score = float(s) * (settings.auto_rerank_weight if c.origin == "auto" else 1.0)
```

**결과**: 수집 논문이 끼어들어 생긴 recall 손해 −0.0085 → −0.0017, 원 논문 수집률 26% → 62%(제목 추정). 코퍼스 크기별 측정으로 예산 2,000청크 + 오래 안 쓴 논문 자동 정리

| 〃 | "DPR … 표로 비교해 주세요" | 표 행까지 숫자 일치 4문장 |
| 사람 판정 세트 50문항 | 단일 논문 20 · 다중 홉 18 · 표·그림·수식 12 | 응답 중앙값 34초 · 인용 확인 뒷받침 단일 58/62 · 다중 홉 86/113 · 표·그림·수식 23/27 |
| 〃 | LLM 검증 | **50/50 '근거 충실'** — 첫 문항은 정답 논문이 근거에 있는데 "찾을 수 없다"고 답한 것도 통과 → 사람 판정이 필요한 이유 |

**대본**: 자기 채점은 50문항 전부를 통과시켰습니다. 문장 단위 확인은 다중 홉 답변에서 4문장 중 1문장꼴로 근거를 넘는 종합이나 인용 누락을 표시합니다. 둘 중 어느 쪽이 사람 판단에 가까운지가 다음 측정입니다.

## 17. 한계와 배운 점

**화면**
- 한계: 답변 채점이 로컬 모델의 자기 채점(시험 50문항 모두 통과 — 사람 판정은 준비만 됨) / 평가 질문 대부분이 코퍼스에서 만든 것 / 인용 확인은 관련도 모델이라 함의를 직접 판정하지 못함(NLI 는 한국어 바꿔 쓰기에 오경보) / 한 사람용
- 배운 점
  1. 작은 표본의 결론은 뒤집힌다 — 평가셋 확대가 가장 큰 개선
  2. 지표는 서로 부딪힌다 — MRR과 다중 홉 recall
  3. 같은 아이디어도 넣는 위치에 따라 득실이 다르다
  4. 자동 테스트는 내 컴퓨터에 숨은 의존성을 드러낸다
  5. 제안이 측정을 통과하지 못하는 일이 많다 — 넣지 않은 결정도 기록한다
  6. 평가 질문의 답이 프롬프트에 들어가면 측정이 부풀려진다

## 18. 다음 방향

| 우선 | 과제 | 기대 효과 |
|---|---|---|
| 1 | 기준 세트 50문항 사람 판정 → LLM 검증·인용 확인·NLI 일치율 | 자기 채점 한계를 숫자로, NLI 켤지 결정 |
| 2 | 실제 사용 질문 → 평가셋(👎 우선), 지표 탭으로 추세 | 평가셋 현실화 |
| 3 | 원 논문 수집 실전 재시험(제목 후보 적용 뒤) | 현재 목표 60% 달성 여부 |
| 4 | 실제 사용에서 다중 홉 실패가 보이면 LLM 반복 검색 | 어려운 질문 recall |

**대본**: 확장할 때도 원칙은 같습니다. 측정 없이 바꾸지 않고, 근거 없는 답은 내지 않습니다.

## 갱신 방법

새 작업이 끝나면 슬라이드를 하나씩 늘리지 않고, 7장 표에 **업데이트 묶음**으로 한 줄 추가하거나 기존 묶음의 결과를 고친다.
수치가 바뀌면 16장(달성률)과 차트(`make_charts.py`)를 다시 만든다. 사람 판정이 끝나면 14장에 일치율(κ)을 넣는다.

## 발표 전에 직접 준비할 것

- 3·9번 슬라이드의 흐름도(PPT 도형으로 그리기)
- 12번: "확인이 필요한 문장"을 펼친 캡처가 필요하면 챗봇에서 같은 질문 후 펼쳐서 캡처
- 코드는 Consolas 등 코드 글꼴 14pt 이상, 전/후를 좌우로 배치
